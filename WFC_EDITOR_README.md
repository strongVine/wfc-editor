# wfc-editor — редактор матриц rotationMap

Tauri-приложение для редактирования файлов `RealmRoadsRotationMap.json` (и аналогичных) — матриц оператора WFC, описанного в `WFC_OPERATOR_CONTEXT.md`. **Это редактор файлов проекта, не игровой движок.** Алгоритмы propagation, коллапса, профили сторон — всё это в C#-проекте Unity. Здесь — только чтение, отображение и запись `.json`.

При работе с этим кодом всегда держи `WFC_OPERATOR_CONTEXT.md` как первичный источник по физике оператора. Этот README описывает только то, что не реконструируется из самого кода.

---

## Стек

- **Tauri 2** (Rust + WebView2 на Windows). Бэкенд минимальный: только подключённые плагины `dialog` и `fs` для системных диалогов и чтения/записи файлов. См. `src-tauri/src/lib.rs` и `src-tauri/capabilities/default.json`.
- **Frontend — vanilla JS, без сборщика, без npm-зависимостей в рантайме.** Подключение скриптов через `<script src=...>` в правильном порядке. ES-модули были опробованы и **не используются** — в Tauri 2 + Vanilla template они дают тихие сбои инициализации без понятных ошибок в консоли. Если соберёшься переходить на ES-модули — сначала проверь что обработчики кнопок реально привязываются.

## Структура файлов

```
src/
  index.html       — разметка, табы, два тулбара (по одному на режим)
  styles.css       — все стили
  main.js          — общее: window.WFC namespace, парсинг/сериализация,
                     mirror(), bitVal/setBit, рендер нибла, валидационные
                     карты, переключение табов
  horizontal.js    — IIFE, режим "Горизонталь": одна матрица, 4 направления
  vertical.js      — IIFE, режим "Вертикаль": две матрицы, ось Up↔Down
src-tauri/         — Rust-часть, конфиг, плагины, иконки, сборка
```

**Принцип организации JS:** `main.js` создаёт `window.WFC = {...}` и кладёт туда константы, утилиты и общие UI-примитивы. `horizontal.js` и `vertical.js` — это IIFE, которые читают `window.WFC` и регистрируют свои `init`-функции обратно в него (`W.initHorizontal`, `W.initVertical`). Состояние каждого режима (`states`, `currentPath`, `dirty`, `validation`, ...) — **приватное внутри IIFE**, не торчит наружу. `index.html` в конце вызывает `WFC.setupTabs()` + оба `init...()`.

## Формат файла

```json
[
  {
    "name": "c0 Outer",
    "rows": [
      "0000FBA6CE000000",   // Front  — d=0
      "0000XXXXXXXXXXXX",   // Right  — d=1
      "0000XXXXXXXXXXXX",   // Back   — d=2
      "0000XXXXXXXXXXXX",   // Left   — d=3
      "0000000000000000",   // Up     — d=4
      "0000000000000000"    // Down   — d=5
    ]
  },
  ...
]
```

Каждая `rows[d]` — ровно 16 hex-символов, по одному на состояние-сосед `B`. Один hex-символ = один nibble = 4 бита поворотов соседа в локальной системе центрального тайла. Семантика битов и направлений — `WFC_OPERATOR_CONTEXT.md` §3, §4.

Состояний может быть от 1 до 16 (`MAX_STATES`). Имена — произвольные строки, никакого формата `"c<N> Name"` редактор не навязывает: что в `name` записано, то и хранится. Pretty-printed JSON с отступом 2.

## Два режима

### Горизонтальный (`horizontal.js`)

Открывает **один** файл. Редактирует строки `rows[0..3]` (Front, Right, Back, Left) каждого состояния. Симметрия — внутри одной матрицы, по формуле §7 для горизонтальной оси (`mirror()` в `main.js`, ветка `d < 4`). Клик по биту атомарно ставит/снимает зеркальный бит в той же матрице.

**Up/Down (`rows[4]`, `rows[5]`) в этом режиме обрабатываются прозрачно**: грузятся как есть, не отображаются в UI, не модифицируются, сохраняются обратно как были. Это важно: вертикальные данные принадлежат другому режиму, и горизонтальный их не должен трогать ни при каких операциях (включая `+ состояние`, где новый стейт получает нулевые `rows[4]` и `rows[5]` через `makeEmptyM()` — корректно, потому что у нового стейта вертикальных связей нет до тех пор пока его не отредактируют в вертикальном режиме).

### Вертикальный (`vertical.js`)

Открывает **два независимых файла** — верхний и нижний слои. Геометрия:

- Верхний слой над нижним. Соседи по вертикали — клетки этих двух слоёв в той же `(x, z)` позиции.
- Верхняя плитка `A` редактирует свою строку `Down` (`rows[5]`) — «что под ней».
- Нижняя плитка `B` редактирует свою строку `Up` (`rows[4]`) — «что над ней».
- Симметрия между файлами: бит в `upper[A].M[5][B] @ r` ↔ бит в `lower[B].M[4][A] @ (4-r)%4`. Та же формула, что в `WFC_OPERATOR_CONTEXT.md` §7 для вертикальной оси.

Колонки таблицы каждого слоя = состояния **парного** слоя. Имена в шапках колонок readonly (правятся только в заголовках своих стейтов).

Наборы состояний слоёв полностью независимы — могут различаться количеством, именами, физическим смыслом.

### Общая UX-логика обоих режимов

- **Add/remove состояний — только в хвост.** Кнопки `+` и `×`, без подтверждений, без проверки ссылок. Допустимое число — 1..16 (`MAX_STATES`). Имя по умолчанию — `c<N>`, где N = новый индекс.
- **Имена редактируются** в заголовке каждого стейта (только в своей матрице).
- **Свернуть/развернуть** стейт — chevron слева от имени; групповые кнопки в тулбаре.

## Валидация симметрии

Снимок, не живая проверка. Запускается при загрузке файла. Сбрасывается при первой же правке (клик по биту, добавление, удаление, переименование) — после этого симметрия поддерживается автоматически и проверять нечего до следующей загрузки.

Подсветка прямо на матрице:
- **Красный заполненный бит** — бит стоит, но парного нет где должен (нарушитель).
- **Бледно-красный пустой бит** — бит должен стоять, но не стоит (дырка, обратная сторона нарушения).

В горизонтальном режиме валидируются только `d ∈ 0..3`. Up/Down не проверяются (в этом режиме они вообще не наша зона ответственности).

В вертикальном режиме валидация запускается только когда **открыты оба файла**; если открыт один — валидации нет (нечего сравнивать).

В статусной строке — счётчик нарушений красным, если они есть.

| Поведение горизонтального режима             | `horizontal.js`                  |
| Поведение вертикального режима               | `vertical.js`                    |

| Зависимости Rust                             | `src-tauri/Cargo.toml`           |
| Иконка, идентификатор приложения, версия     | `src-tauri/tauri.conf.json`      |

## Чего не делать без серьёзной причины

- **Не менять формат `.json`.** Его же читает C#-движок Unity-проекта. Если потребовалось что-то новое — обсудить через расширение, а не подмену.
- **Не править формулу `mirror()`** не сверившись с `WFC_OPERATOR_CONTEXT.md` §7. Расхождение между этой функцией и движком означает что редактор будет ставить «зеркальные» биты в местах где их движок не ожидает — фактически порождать асимметричные матрицы тихо, без диагностики.
- **Не позволять горизонтальному режиму редактировать `rows[4]`/`rows[5]`** и наоборот вертикальному — `rows[0..3]`. Эта изоляция — гарантия что один режим не портит данные другого.
- **Не использовать `localStorage`/`sessionStorage`/IndexedDB.** Tauri WebView их вроде поддерживает, но привязка к WebView2 хрупкая. Все нужные настройки персистентности — через файловую систему (плагин `fs`).
- **Не вводить ES-модули** без проверки на работающую сборку. См. секцию «Стек».

## Запуск и сборка

```
npm run tauri dev      # dev-режим, hot reload, DevTools по F12
npm run tauri build    # release-сборка, exe в src-tauri/target/release/bundle/
```

Release-сборка — самостоятельный exe. На целевой машине нужен только WebView2 (есть на Windows 11 и свежих Windows 10 по умолчанию).
